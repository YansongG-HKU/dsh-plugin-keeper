# 插件锻造炉 · dsh-plugin-smith

把一句插件需求，锻造成一条**可复核的安装记录**：侦察候选 → 验毒审计 → 判断满血/残血/阉割 → 补齐缺口 → 测试验收 → 由你确认安装。

它不是插件市场。市场是「逛」，锻造炉是「采购 + 质检 + 定制 + 验收」：你只说你要什么，它去找、去验、去补、去造，最后只把「要不要按下安装」这一个决定交给你。

> **兼容性（DSH 0.2.2-rc.1）**：Host 侧只使用 tools.register / systemPrompt.section / webServer.register 等稳定接口，0.2.2-rc.1 下无破坏性变化；104/104 测试通过。唯一已知软降级：`profileContext.dir` 在 0.2.2 不再公开，L4 安装目录摘要校验会回退为「未知目录」，不影响安装主流程（可用 `DSH_PROFILE_DIR` 显式指定）。

```
需求 ──▶ 立案 ──▶ 侦察 ──▶ 验毒 ──▶ 血量/缺口 ──▶ 决策 ──▶ 执行 ──▶ 验收 ──▶ 安装
         │         │        │           │            │        │        │        │
         └─────────┴────────┴───────────┴────────────┴────────┴────────┴────────┘
                              同一条记录、同一份证据链（面板实时可见）
```

## 它解决什么

- **找**：同时查插件市场索引、npm、GitHub、社区反馈（下载量、star、最近提交、维护者），按契合度 / 质量 / 维护度 / 风险打分，给出候选对比。
- **验**：本地包做静态供应链审计（安装脚本、`eval`、子进程、网络出口、文件写入、凭据访问、混淆、依赖面、patch 是否遮蔽官方行）；registry 包先做元数据审计（弃用、安装脚本、陈旧度、仓库与 license、用量），**再把发布 tarball 下载到临时目录、解包、按源码做静态审计、随即删除**——装前拿不到源码的问题已解决；下载/解包失败时降级为元数据级并在记录里标注。不安全直接淘汰。
- **隔离试装**（sandbox 证据，`depth=deep` 自动开启或 `sandbox:true`）：在临时目录里用 profile 自带 pnpm 以 `--ignore-scripts` 真正解析并落地候选包，证明落地产物的 sha256 摘要与审计对象完全一致，然后删除目录。不碰你的 profile、不执行包内任何脚本，证据等级从 `static` 升为 `sandbox`。
- **判**：把候选拆成「能力 × 状态」清单，找出**阉割（cut）、残缺（incomplete）、过时（stale）、缺集成（integration）、体验（ux）**，给出 0–100 血量分。
- **补**：残血/阉割**不允许直接装**。决策变成 `complete-then-install`：按缺口清单补齐、保留上游来源与 license、重新验收，再进入安装确认。
- **造**：没有可用候选时 `build`，从零锻一个 DSH bundle，同样过门禁。
- **测**：L0 manifest/patch/JS 语法 → L1 自带测试 → L2 profile 实际加载确认 → L3–L5 行为/完整性/回滚证据。任一级失败即拦截，验收通过才算完成。
- **装**：安装必须由你在面板点击。Host 会先 `inspect` spec、对本地 bundle 复跑 L0、安装后用 profile 自己的清单确认 L2，并写入安装历史与回滚点。
- **留痕**：每条需求是一份 JSON 记录，含候选、审计发现（带文件/行号/证据片段）、缺口、决策理由、验收项、安装结果、回滚方式、关联会话。

## 两个入口，同一条记录

1. **面板**：侧边栏「插件锻造炉」→ 输入需求 → 「立案」。之后所有推进、决策、验收、安装都在这里看。
2. **会话**：直接在任意会话里说「给我找个能做 X 的插件」。模型会调用 `plugin_scout` 工具建同一条记录并跑同一条流水线；面板实时显示进度，也能接着让你确认。

面板和工具调用同一个 Host 服务，没有第二套逻辑。

## 安装

仓库：https://github.com/YansongG-HKU/dsh-plugin-smith

```bash
# 从 GitHub 安装（推荐）
dsh plugin --profile desktop add github:YansongG-HKU/dsh-plugin-smith

# 或本地开发目录
dsh plugin install <本目录绝对路径>
```

或让 Harness 的 `plugin_manager` 以 `install_bundle` 安装本目录。安装后重启/刷新 Web 页面即可在侧边栏看到。

数据落在 `$DSH_HOME/plugin-smith/records.json`（默认 `~/.dsh/plugin-smith`），安装历史在同目录 `history.json`。可用 `apply(ctx, { dataDir })` 覆盖。

## 面板做什么

- 顶部：需求输入（快筛 / 标准 / 深挖三档深度）。
- 统计：总记录 / 进行中 / 待你拍板 / 已安装。
- 记录列表：状态、血量（满血/残血/阉割 + 分数）、安全分、候选数、主操作按钮；增补过的记录带 `rev N` 徽章，复查过缺口的带 `第N轮` 徽章。
- 详情：需求与能力拆解（含**修订列表 + 补充需求入口**）、候选对比、审计报告（按严重度的发现 + 证据位置 + 能力面清单 + 隔离试装）、血量与缺口（**第 N 轮**、补齐方案/工作量/风险、**复查缺口**按钮）、决策与计划、执行进度、L0–L5 验收表、安装记录与回滚、备注与时间线。
- 操作：立案、补充需求、复查缺口、去会话推进、安装、回滚、归档、重开、否决、备注、调深度。

安装是**用户专属动作**：模型调用 `install` 会收到 `requiresUserConfirmation`，只有面板点击会写入用户授权。

## 需求会变：增补与复查循环

一条记录不是一次性的工单，它跟着需求走：

1. 你在详情里任何阶段都可以「补充需求」→ 记录升到 `rev N`，能力/约束会随附快照，历史保留每次增补。
2. 增补会**立刻作废旧决策**并**标记缺口分析过期**：`decision` 清空、`blood.stale = true`、状态回到「分析中」。安装门禁同时拒绝旧决策（`decision.intentRev` 落后）和过期缺口。
3. 点「复查缺口」→ 会话拿到一份 gap 简报：按最新需求逐条重判能力，用 `blood({next_round:true})` 写第 N+1 轮缺口，再重新决策——满血就装，仍有缺口就继续补齐，形态不对就自建。
4. 每一轮缺口的分数、标签、缺口数都记在 `bloodRounds` 里，面板显示「第 N 轮 · 复查」，复核时能看清需求是怎么长出来的、每一轮补了什么。

## 模型工具 `plugin_scout`

一个工具、十三个动作，描述里带着完整操作手册：

`intake` · `get` · `amend` · `update` · `candidates` · `audit` · `blood` · `decide` · `verify` · `install` · `rollback` · `history` · `claim_session`

`intake` 建记录并返回下一步；`amend` 追加需求修订；`audit` 传 `path`（本地包）或 `package_name`（registry 包，默认会下载 tarball 做源码级扫描，`source:false` 可退化为元数据级）；`blood` 写缺口（需求增补后的复查传 `next_round:true`）；`decide` 过决策门禁；`verify` 跑验收门禁；`install` 会被用户授权检查拦下，直到你在面板点了安装。

## 硬规则（写在代码里，不靠自觉）

1. 没有审计报告，不允许进入安装类决策。
2. 审计 `unsafe` 或安全分 < 60，Host 拒绝安装。
3. 血量不是 `full`，不允许 `install`，只能 `complete-then-install` 或 `build`。
4. 验收未通过，Host 拒绝安装。
5. 安装必须由用户在面板确认；模型不能代按。
6. 后装物必须与审计对象一致：本地 bundle 安装前复跑 L0；registry 包安装前 `inspect`；安装后除 L2 加载确认外，还做 **L4 内容摘要比对**（审计时对源码算 sha256 摘要，装完后对 profile 里的安装目录重算，不一致即判失败并要求回滚）。
7. **需求变更即失效**：`rev` 变化后，旧决策（`decision.intentRev` 落后）和旧缺口分析（`blood.stale`）都不能再用；必须先做新一轮缺口分析再决策，Host 门禁同样拦截。
8. 所有动作写入记录历史，含 `force` 越权及其理由。

## 验收（这个插件自己的）

```bash
node --test "test/*.test.mjs"
```

覆盖：记录模型与投影、血量打分、决策门禁、状态机、持久化、审计引擎、验收门禁、registry 源码级审计（本地 registry + 真实 tarball 解包/扫描/清理）、隔离试装、**需求增补与多轮缺口复查**（修订历史、决策失效、过期门禁、`bloodRounds`、gap 简报）、面板 HTTP 接口（挂载 `apply()` 后用假请求跑真实路由，含 amend/claim-session gap）、**完整安装链路 L0→L2→L4→回滚 L5**（等价 profile 目录 + fake pluginManager，含篡改拦截与「模型不可代按」）。逐条验收矩阵见 [docs/ACCEPTANCE.md](docs/ACCEPTANCE.md)。

## 已知边界

- 静态审计只能证明「没有发现明确恶意模式」，不能证明「绝对安全」；面板会标注证据等级（static / sandbox / behavioral）与审计范围（源码级 / 元数据级），不夸大。
- 源码级审计覆盖 npm 发布包；GitHub 直链与私有 registry 目前走元数据或本地目录路径。tarball 超过 30MB、下载失败或解包失败时自动降级并记录原因。
- 隔离试装（sandbox）只做「脚本禁用的落地 + 摘要一致」：不执行候选代码、不启动 Harness；运行时行为观测（behavioral）仍在后续版本。
- GitHub / npm 数据受网络与限流影响，取不到时审计降级而不是失败。
